# Channels — полный аудит и план переработки

Дата: 2026-10-04
Репозиторий: babichdenis/Channels

## Резюме

Система уже имеет хорошие базовые части:

- отдельный `news_conveyor.py`;
- `NEWS_GENERATOR.md` + `NEWS_WRITER_STYLE.md`;
- кластеризацию новостей;
- очередь `queue.json`;
- отдельный `repost.py`;
- отдельный `gen_images.py`;
- approval-бот;
- scheduler;
- SimHash-дедупликацию.

Но сейчас pipeline устроен так, что несколько этапов могут пропустить артефакт, а последний этап публикации его не блокирует.

Главная переработка:

```text
SOURCE
  ↓
INGEST
  ↓
NORMALIZE
  ↓
SOURCE / PROMO CLEAN
  ↓
CLUSTER
  ↓
EVIDENCE / VERIFICATION
  ↓
NEWS GENERATOR
  ↓
NEWS WRITER
  ↓
CONTENT GUARD
  ↓
MEDIA GUARD
  ↓
APPROVAL
  ↓
FINAL PUBLISH GATE
  ↓
TELEGRAM
```

## P0 — критично

### 1. Нет единого финального Content Guard

`repost.py` очищает текст, но `scheduler.py` перед отправкой не проверяет, что в финальном тексте осталась реклама/ссылка на Telegram/самореклама.

Это означает:

```text
repost.py
  ↓
clean_source_text()
  ↓
approval_bot
  ↓
ручная перегенерация
  ↓
queue.json
  ↓
scheduler
  ↓
ПУБЛИКАЦИЯ
```

Любой промежуточный этап может вернуть рекламу обратно.

**Исправление:** один обязательный `content_guard.py`, который вызывается непосредственно перед Telegram API.

---

### 2. Очистка репостов слишком слабая

Сейчас очистка завязана на:

- короткие строки;
- конкретные слова;
- `t.me`;
- `@handle`;
- имя источника.

Проблема: длинный рекламный блок может не попасть под правило `len(line) < 220`.

Например:

```text
Мы подготовили для вас новый материал...
Подписывайтесь...
Читайте больше...
Наш канал...
```

может пройти как обычный контент.

**Исправление:** удалять рекламные блоки построчно + проверять весь финальный текст.

---

### 3. Approval bot может снова испортить репост

`approval_bot.py` умеет перегенерировать/переписывать текст.

После такой операции нет обязательного повторного content guard.

**Исправление:**

```text
любой rewrite
    ↓
CONTENT GUARD
```

---

### 4. Изображения действительно режутся кодом

Найдено два места.

`gen_images.py`:

```python
image = image.crop((0, 0, image.width, int(image.height * 0.92)))
side = min(image.width, image.height)
left = (image.width - side) // 2
image = image.crop((left, 0, left + side, side))
```

Это физически:

1. отрезает 8% изображения;
2. затем кадрирует его в квадрат.

`news_conveyor.py` делает похожее:

```python
image = image.crop((0, 0, image.width, int(image.height * 0.92)))
```

Причина — попытка убрать watermark.

**Это надо удалить.**

Правило v2:

> Исходное изображение репоста никогда не crop-ится.

> Сгенерированное изображение никогда не crop-ится автоматически.

Если файл не проходит технический лимит Telegram — либо пропускаем медиа, либо делаем пропорциональное техническое уменьшение, но не кадрирование.

Telegram `sendPhoto` допускает фото до 10 MB, сумму ширины и высоты до 10000 и соотношение сторон до 20.

## P1 — новости

### 5. Конфликт «2 источника» и реальной логики

`00_GLOBAL_RULES.md` говорит:

```text
news → подтверждение 2+ источника
```

Но `news_conveyor.py` содержит:

```text
Единственный источник — нормально
```

То есть более специфичный runtime-contract фактически ослабляет глобальное правило.

Нужно выбрать одну модель.

Рекомендация:

### Не требовать механически 2 источника для каждого события.

Использовать evidence policy:

| Evidence | Действие |
|---|---|
| официальный первичный источник | можно публиковать |
| официальный + независимый | максимальный приоритет |
| 2 независимых СМИ | можно публиковать |
| один вторичный источник | manual review |
| Telegram-пересказ без первоисточника | reject |
| слух / «готовится» / инсайд | reject |

Это лучше, чем тупое `sources >= 2`.

---

### 6. Сейчас «2 источника» не означает 2 независимых источника

Кластер может содержать:

```text
gnews_en_openai
gnews_ru_openai
gnews_en_anthropic
```

и считаться как 3 источника.

Но Google News может просто пересказывать один и тот же первоисточник.

Нужно считать:

```text
unique_source_domains
+
source_class
+
primary/secondary
```

а не только количество RSS records.

---

### 7. NEWS_GENERATOR не должен писать

Сейчас архитектура уже близка к правильной:

```text
NEWS_GENERATOR
→ проверка события

NEWS_WRITER_STYLE
→ написание
```

Это надо сохранить.

Но `NEWS_GENERATOR` должен возвращать ещё:

```json
{
  "event": "...",
  "actor": "...",
  "change": "...",
  "event_date": "...",
  "evidence": [
    {
      "source": "...",
      "url": "...",
      "type": "primary|secondary",
      "supports": ["..."]
    }
  ],
  "verification": "verified|partial|manual_review"
}
```

---

### 8. Новость должна собираться из EVENT, а не из длинного source dump

Правильная схема:

```text
raw sources
    ↓
evidence extraction
    ↓
event object
    ↓
writer
```

А не:

```text
6000–12000 символов источников
    ↓
LLM
    ↓
«сделай новость»
```

Иначе модель начинает смешивать:

- факты;
- мнение автора;
- старый контекст;
- рекламные заявления;
- выводы.

## P1 — качество

### 9. QC fail-open

В `conveyor.py`:

```python
if QC недоступен:
    return {"status": "PASS"}
```

Это опасно.

Если QC сломался, материал автоматически проходит.

Нужно:

```text
QC error → manual_review
```

Никогда:

```text
QC error → PASS
```

---

### 10. `looks_garbage()` слишком грубый

Функция считает наличие:

```text
<
>
|
\
{
}
```

мусором.

Для обычного текста это допустимо.

Но новости могут содержать:

- HTML;
- ссылки;
- цитаты;
- специальные Telegram entities.

Нужен отдельный parser/normalizer перед проверкой.

## P2 — архитектура

### 11. Названия каналов уже разъехались

В коде одновременно встречаются разные бренды:

```text
НейроХитрости
НейроСекреты
Нейропомощник
ПромптКлад
НейроСигнал
```

Это не ломает публикацию, но создаёт путаницу для агентов.

Нужен один `CHANNELS.json` как единственный источник истины.

---

### 12. Канальные правила не должны быть размазаны по Python

Сейчас часть логики находится:

- в `CHANNELS.json`;
- в `config.json`;
- в `conveyor.py`;
- в отдельных prompt-файлах.

Рекомендация:

```text
CHANNELS.json
→ identity
→ audience
→ role
→ tone
→ rubrics
→ boundaries
→ publish policy

PROMPTS/
→ editorial behavior

Python
→ orchestration only
```

## Главный принцип

Не пытаться сделать LLM умнее.
